** DONE [#C] Verify the secret-read deny merge behavior live
:PROPERTIES:
:FILE: agent/orchestrator.md
:END:

Verified live in a real session (2026-08-01): reading a =*.env= file as
the orchestrator, rust-dev, and web-dev is hard-denied ("Do not read .env
files") rather than prompting. The agent-level re-denial works.

Two side findings surfaced while verifying:

- A =.env.example= read is also denied, despite the
  ="*.env.example": allow= rule that follows the ="*.env.*": deny=.
  The config comments claim "last-match-wins", but matching behaves as
  deny-wins: the =.env.*= deny shadows the =.env.example= allow, making
  the allow rule dead code. Harmless (denying =*.env.example= is safer),
  but the comments in =agent/*.md= and the global config describe
  behaviour that does not hold.
- A text file named =*.gpg= was readable, so the ="*.gpg": deny= did not
  fire in the probe. Real =.gpg= files are binary and the Read tool
  refuses binary files anyway, so practical exposure is low, but the
  rule's effectiveness is unconfirmed.

** DONE [#C] Confirm permission matching semantics (deny-wins vs last-match-wins)
:PROPERTIES:
:FILE: docs/ROADMAP.org
:END:

The live verification of the secret-read denies found that permission
matching does not behave as the config comments document. The comments in
=agent/orchestrator.md=, =agent/rust-dev.md=, =agent/web-dev.md=, and the
global =~/.config/opencode/opencode.jsonc= say rules are evaluated
"last-match-wins", but:

- =.env.example= (allow, listed after the =.env.*= deny) is denied,
  implying deny-wins or deny-first evaluation.
- A text file named =*.gpg= was readable, so the =*.gpg= deny did not
  fire in that probe.

Resolved (2026-08-01) against the official Permissions docs
(https://opencode.ai/docs/permissions/, updated 2026-07-31): "Rules are
evaluated by pattern match, with the last matching rule winning." The
config comments are correct, and the docs' own default =read= example
uses the same =*.env= deny / =*.env.*= deny / =*.env.example= allow
ordering, so the =.env.example= allow is not dead code. The earlier
probe observation is most likely a probe artifact (read-path matching,
or the allow rule shadowed at runtime by the older engine version); no
config change was needed. The =*.gpg= deny is kept as a harmless
belt-and-braces rule: real =.gpg= files are binary and the Read tool
refuses binary files regardless.

** DONE [#C] Investigate reviewer subagent empty responses
:PROPERTIES:
:FILE: agent/reviewer.md
:END:

Root cause found and fixed. The empty results were not a streaming
quirk: every request for =deepseek-v4-pro-thinking= through the
Anthropic-compatible endpoint fails with =AI_APICallError: Bad Request=
(HTTP 400) — verified in =~/.local/share/opencode/log/opencode.log=
(4/4 attempts across two sessions, 2026-08-01). The model is the only
one registered with =thinking: enabled= options and a 262144-token
output limit, one of which the DeepSeek API rejects.

Fix: reviewer and reasoning-engineer (same model, equally broken, just
unexercised) switched to =deepseek/deepseek-v4-pro= as a fallback.
README documents the switch and the condition for re-enabling
pro-thinking.

Note: agent definitions are cached for the lifetime of an OpenCode
session, so the fallback only takes effect in a new session.

** DONE [#C] Reviewer: document the pipe-based bash write bypass
:PROPERTIES:
:FILE: agent/reviewer.md
:END:

The ="*": deny= catch-all blocks direct mutation, but OpenCode matches
bash patterns on command prefixes, so a pipe such as =git diff | git apply=
still executes and can write. Accepted as residual risk for now; the same
behaviour exists in the global config.

Fixed (2026-08-01): the accepted risk is now documented in the reviewer
prompt's bash permission block, with a note to revisit if OpenCode gains
argument- or pipe-aware matching.
